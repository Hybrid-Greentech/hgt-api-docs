## What a resource is

A **resource** is a single device the platform dispatches individually, identified by a `resourceId` you choose. Resources are one of many like-typed devices you offer to the platform.

An **asset** is a dispatchable installation under delegated or direct control, identified by an `assetId`. The two are never interchangeable in dispatch or settlement, and they use separate APIs.

| Resource type | `resourceType` | Typical scale |
|---------------|----------------|---------------|
| EV charger | `evCharger` | Residential and commercial charge points, integrated through an OCPP backend. |
| Heat pump | `heatPump` | Residential and small commercial units. |
| Battery | `bess` | Residential and small commercial storage. |
| CHP | `chp` | Combined heat and power units, which export electricity |
| P2X | `p2x` | Power-to-X plants, which convert electricity into another carrier |
| PV | `pv` | Residential and small commercial rooftop and ground-mount arrays |
| Other | `misc` | Dispatchable equipment with no resource type of its own yet |
| CHP | `chp` | Combined heat and power units, which export electricity. |
| P2X | `p2x` | Power-to-X plants, which convert electricity into another carrier. |
| PV | `pv` | Residential and small commercial rooftop and ground-mount arrays. |
| Other | `misc` | Dispatchable equipment with no resource type of its own yet. |

Larger batteries integrate through [OEM Integration](/controller/overview), where the platform drives the hardware directly, or through [Individual Sites](/delegated-operators/welcome), where a third party closes the control loop. The choice is about who closes the loop and at what scale, not about the equipment.

## One message set for every type

Registration, telemetry, events, dispatch, and acknowledgement are identical across resource types. A resource type determines exactly two things:

| Determined by resource type | Where it appears |
|-----------------------------|------------------|
| Which metrics the resource publishes | The measurements channel — see [Metrics](/data-standards/metrics) |
| Which equipment properties it declares | The `configuration` block at registration |

Everything else — the topic tree, the envelope, the setpoint semantics, the acknowledgement contract — is shared. Onboarding a new resource type costs one enum value and, where the equipment has dispatch-relevant properties to declare, one configuration variant. `chp`, `p2x`, and `misc` declare none, so their `configuration` is an empty object. `pv` declares one, because production forecasting reads where the array sits and how it is oriented, and nothing else on the wire carries that.

## Transport

| Environment | Host | Port | Protocol |
|-------------|------|------|----------|
| Sandbox | `aggregator.gridhub.dev` | `8883` | MQTTS |
| Production | `n1.link.gridhub.ai` | `8883` | MQTTS |

All topics follow the pattern:

```
{priceZone}/{customerName}/v2/{channel}/{resourceId}
```

| Segment | Description |
|---------|-------------|
| `priceZone` | Grid bidding zone. One of `DK1` or `DK2`. |
| `customerName` | Namespace assigned during onboarding. |
| `v2` | API version segment. |
| `channel` | One of `register`, `update`, `measurements`, `events`, `activation`, or `acknowledgement`. |
| `resourceId` | The resource the message concerns. Absent on `register`, which carries an array. |

Neither the site nor the portfolio appears in the topic. Portfolio membership is administrative, and a resource that moves between portfolios keeps its topic and its credentials.

| Channel | Direction | QoS | Retained |
|---------|-----------|-----|----------|
| `register` | Resource to platform | 1 | No |
| `update` | Resource to platform | 1 | No |
| `measurements` | Resource to platform | 0 | No |
| `events` | Resource to platform | 1 | No |
| `activation` | Platform to resource | 1 | No |
| `acknowledgement` | Resource to platform | 1 | No |

Use a clean session. Measurements are published at QoS 0 because a sample redelivered by a broker retry is already outside its delivery bound.

## Control model

The platform commands an absolute, signed power setpoint. Two commands exist:

| Command | Effect |
|---------|--------|
| `Setpoint` | Moves the resource to a signed power value now, and holds it until released or until `endsAt`. |
| `Release` | Returns the resource to its own control logic. |

A setpoint is a **target**, not a ceiling. You apply the nearest value your declared `controlGranularity` allows, and `measuredPower` reports what you achieved.

<Warning>
  A release is not a setpoint of `0`. Zero power is a valid instruction to hold zero power, and the resource stays under platform control until it is released.
</Warning>

Resource types differ only in the range they occupy. That difference is declared at registration, not carried in the message:

| Resource type | Setpoint range |
|---------------|----------------|
| `evCharger` | `[-maxImportKw, 0]` |
| `heatPump` | `[-maxImportKw, 0]` |
| `p2x` | `[-maxImportKw, 0]` |
| `chp` | `[0, maxExportKw]` |
| `pv` | `[0, maxExportKw]` |
| `bess` | `[-maxImportKw, maxExportKw]` |
| `misc` | `[-maxImportKw, maxExportKw]`, whichever ends the equipment declares |
| `misc` | `[-maxImportKw, maxExportKw]`. Either end is `0` when the equipment cannot reach it. |

## v1 EV charger and heat pump APIs

The v1 APIs remain published and fully operational. No sunset date is set.

| API | Status |
|-----|--------|
| [EV Chargers v1](/ev-chargers/quickstart) | Deprecated. Operational for existing integrations. |
| [Heat Pumps v1](/heat-pumps/quickstart) | Deprecated. Operational for existing integrations. |

New integrations use v2. Migration is per resource: a resource is on v1 or on v2 depending on which topic prefix it publishes to. See [Migrating to v2](/distributed-resources/migration).
