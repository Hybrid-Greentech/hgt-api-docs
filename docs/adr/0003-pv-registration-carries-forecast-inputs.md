# PV registration carries forecast inputs

Every other resource type declares only what bounds a dispatch: an EV charger's current type, a heat pump's staged ratings, a battery's power and energy limits, or — for `chp`, `p2x`, and `misc` — nothing at all. PV breaks that pattern. `pvConfiguration` declares `latitude`, `longitude`, and a `moduleGroups` array of `{ capacityKwp, azimuth, inclination }`, none of which any setpoint path reads. They exist because the platform forecasts a resource's production, and for a rooftop array the geometry that drives that forecast exists nowhere else the platform can reach: it deliberately does not model sites, so there is no site record to hang coordinates on, and no measurement reveals which way a roof faces.

## Considered options

- **Reuse `emptyConfiguration`, as `chp` and `p2x` do.** Rejected: it is the same shape but a different situation. Those types declare nothing because the platform would branch on nothing. PV has a platform function that reads registration, so an empty block does not defer a decision — it withholds an input the forecast needs and cannot obtain.
- **Collect the array geometry out of band, during onboarding.** Rejected: it puts the geometry outside the `update` channel, so a resource that adds panels or re-pitches a roof has no way to tell the platform, and the record drifts from the equipment with nothing to detect the drift.
- **Mirror the internal PV model verbatim.** Rejected in parts. The `metadata` block (manufacturer, build year, communication protocol) is identity data, which `bessConfiguration` already excludes by policy. `address` is identity and `timezone` is derivable from the coordinates. `storage_capacity` is `0` for PV. `specification.power` reads like an inverter rating but is populated with the array's DC capacity, draws no rated-versus-usable distinction, and duplicates the sum of the module groups; `maxExportKw` is already the AC envelope, so the clipping ratio falls out of the two numbers the wire already carries.
- **Three required fields plus one optional** (chosen). Forecast inputs only, and nothing that identifies or restates.

## Consequences

- **Registration is where the platform learns what it cannot measure**, not only what bounds a setpoint. PV is the first type to exercise that reading, and the rule generalises: a future type whose platform-side model needs a physical property declares it here rather than in a side channel.
- **Azimuth is south-based on the wire, matching the platform model.** `0` is South, positive toward East, in the range `-180` to `180`, referenced to true rather than magnetic south. The wire therefore needs no conversion at the boundary, which is the point: a translation layer between the published contract and the forecaster is a place for a sign error to live, and a mirrored azimuth is unfalsifiable from the value alone.
- **The cost is that geographic azimuth is the more widely known convention.** Mapping, GPS, and WMM all measure clockwise from north, so an integrator's intuition and half the design tools disagree with the contract. Worse, agreeing on a south origin is not sufficient: at least one widely used tool measures from south with **west** positive, which mirrors east and west while staying inside the valid range. The published docs therefore state the contract as a cardinal table and warn about both conversions — the from-north shift, which moves production by half a day, and the sign mirror, which swaps morning for afternoon. No vendor is named: a census of tool conventions would rot on someone else's release schedule.
- **`systemLoss` is optional with a documented default of `0.14`.** A residential installer does not hold a system-loss figure, so requiring it would collect a guess the platform could not distinguish from a measurement. The cost is accepted knowingly: forecast quality varies by whether an integrator supplies it, and the default is published so the difference is visible rather than silent.
- **`configuration` is replaced wholesale on `update`.** The update payload references the same `resourceConfiguration`, so there is no per-field merge inside the block: extending an array resends the coordinates and every group. This was already true of the battery's eight fields and went undocumented; the array makes it routine, because arrays get extended and roofs do not.
- **A hybrid site registers two resources**, the battery as `bess` and the array as `pv`, each with its own `resourceId` and its own setpoints. Both publish `siteImport` and `siteExport` from the one meter, which the no-cross-resource-consistency rule already licenses.
- **`measuredPower` for a PV resource is AC production at the inverter output**, independent of where the power goes. The alternative — net exchange with the grid — would report `0` for a fully self-consuming array while `availablePowerDown` claimed its whole production, breaking the invariant that headroom is read from the measured position.
- **Curtailment is a downward activation.** A PV resource at full production has `availablePowerDown` equal to its production and `availablePowerUp` of `0`; a curtailed one has upward headroom equal to what the curtailment withholds. Both fall to `0` at night, so PV is the mirror image of `chp`, which idles with its whole envelope available upward.

## Deferred

- **Trackers.** `inclination` is degrees only, because a tracking array at residential or small commercial scale is rare and a 40 MW single-axis plant is on the OEM path. A `tracking` enum is purely additive if one ever registers as a resource.
- **Module group labels.** The internal model names and describes each group. The platform reads neither, so they stay off the wire until an integrator needs them round-tripped.
- **A PV inverter AC rating distinct from `maxExportKw`.** Nothing in the platform reads one today.
