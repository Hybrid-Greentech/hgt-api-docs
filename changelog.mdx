<Update label="September 2, 2026" tags={["delegated-operators", "fix", "feature", "breaking-change"]}>
  ## Activation reference corrected, heartbeat documented

  The Activations reference did not describe the messages the platform actually publishes. Four of its five fields were wrong. The wire itself has not changed — this is a correction to the documentation, not to the API — but code written against the previous reference will not parse a real activation.

  ### Corrected activation payload (v3.2.0)

  | Previously documented | Actual field |
  |-----------------------|--------------|
  | `eventId` (string) | `messageId` — a ULID, generated per message |
  | `timestamp` (integer, epoch milliseconds) | `timestamp` — an RFC 3339 timestamp in UTC |
  | `powerkW` (number) | `setpoint.value`, with `setpoint.unit` always `kW` |
  | not documented | `status` — always `ACTIVE` |

  All five fields are always present. The reference previously marked only `timestamp` and `task` as required. `task` no longer declares a UUID format, because the platform sends it as an opaque string.

  - **`setpoint.value` is signed.** It follows the generator convention: export is positive, import is negative.
  - **A setpoint of `0` deactivates the asset.** There is no separate stop message and no change of status.
  - **`status` is always `ACTIVE`.** It is retained for backward compatibility and never varies. Don't branch on it.

  ### Heartbeat channel

  The platform publishes a heartbeat for every asset once per second on `{priceZone}/{customerName}/heartbeat/{assetId}`, carrying an `eventId` and a `value` that alternates between `0` and `1`. This channel already existed but was never documented. No action is required.

  ### Transports

  Production accepts MQTT over TLS on TCP at `n1.link.gridhub.ai:8883`, and MQTT over secure WebSockets at `wss://n1.link.gridhub.ai:8084/mqtt`. Sandbox accepts TCP only. The reference previously declared the `mqtt` scheme for both environments, which implied an unencrypted connection on the TLS port.

  Timestamps on the task, task event, event, and measurement channels are unchanged and remain integer epoch milliseconds. Only activations carry RFC 3339.
</Update>

<Update label="August 3, 2026" tags={["delegated-operators", "feature", "deprecation", "breaking-change"]}>
  ## Data standards now keyed on market

  Telemetry and response requirements have moved to their own [Data Standards](/data-standards/overview) section and are now determined by the **market** an asset is prequalified for, rather than by its asset class. Device type still determines which metrics you publish; the market determines how fast they flow and how quickly the asset must answer a dispatch.

  Requirements are resolved once, at prequalification, from the strictest market the asset is prequalified for. They do not change when a task starts or ends.

  ### What this changes for your integration

  - **New metrics.** Available power up and down are now required for every device type on the Delegated Operators API, not for batteries alone. Available energy up and down are required for batteries. See [Metrics](/data-standards/metrics).
  - **State of charge tightens** from a 5 second to a 1 second bound.
  - **Grid frequency is mandatory** for the frequency-responsive markets — FFR, FCR-D, FCR-N and FCR — rather than optional where a site happens to measure it.
  - **Delivery lag is now per market.** It remains 250 ms for the fast markets and relaxes to 5 s for mFRR and wholesale.
  - **Response bounds are per market**, and apply only when the platform issues activations. Under local control you answer to the TSO's activation profile directly.
  - **`wholesale` replaces day-ahead, intraday continuous, and intentional imbalance** as a single market with one set of bounds.

  Existing integrations remain compliant until their next prequalification. New integrations meet these requirements from day one.

  ### Schema changes (v3.1.0)

  All changes are additive. No topic, endpoint, or payload shape has changed, and no existing enum value has been removed.

  - **`measurementType`** gains `availablePowerUp`, `availablePowerDown`, `availableEnergyUp`, `availableEnergyDown`, and `mfrrBaseline`.
  - **`units`** gains `kWh`.
  - **`taskType`** gains `ffr`, `fcr`, `mfrr`, and `wholesale`.
  - **`powerDc`** is deprecated. It is diagnostic only and no longer part of the data requirements.
  - **`dayahead`** is deprecated in favour of `wholesale`. The platform maps it, and the enum value remains so that existing publishers do not fail validation.

  The EV charger and heat pump APIs are unchanged. The market bounds apply to them, using the metrics those APIs already define.

  <Note>
    `/delegated-operators/data-standards` now redirects to the new section.
  </Note>
</Update>

<Update label="July 30, 2026" tags={["delegated-operators", "fix", "deprecation"]}>
  ## Data Standards page, telemetry rate fixes

  The new [Data Standards](/data-standards/overview) section defines the telemetry rates and control-response requirements for the Delegated Operators integration. Where another page or diagram states a different rate, use the values in that section.

  No schema, topic, or endpoint has changed. If your integration already meets these rates, no action is required.
</Update>

<Update label="July 15, 2026" tags={["ev-chargers", "heat-pumps", "delegated-operators", "rest-api"]}>
  ## Initial API documentation release

  This release publishes the first version of the HGT platform developer documentation, covering all three integration surfaces.

  ### EV Chargers — OCPP MQTT API (v3.0.2)

  - **Registration:** Single and bulk resource registration via `v1/register` and `v1/bulk/register`
  - **Measurements:** Power telemetry via `v1/power/{resourceId}`
  - **Status events:** OCPP status reporting via `v1/status/{resourceId}`
  - **Activations:** v1 and v2 activation message formats on `v1/activation/{resourceId}`; v2 adds `resource_id` to the payload
  - **Bulk activations:** Multi-resource power limit dispatch via `v1/bulk/activation`
  - **Acknowledgements:** Required per activation; acceptance codes cover all rejection scenarios
  - **Updates:** Partial resource modification via `v1/update/{resourceId}`

  ### Heat Pumps — MQTT API (v3.0.1)

  - **Registration:** Resource registration with rated compressor and backup heater power
  - **Measurements:** Availability telemetry (upward and downward kW) via `v1/measurement/{resourceId}`
  - **Status events:** Directional status reporting (`Available`, `ActivatedUp`, `ActivatedDown`, `Unavailable`)
  - **Activations:** Directional commands (`ActivationUp`, `ActivationDown`, `Release`) via `v1/activation/{resourceId}`
  - **Zonal schedules:** Optional daily availability profiles via `v1/schedules/zonal`

  ### Delegated Operators — MQTT API (v3.0.1)

  - **Tasks:** Market task dispatch over `tasks/{assetId}` with 30-second acknowledgement window
  - **Activations:** Real-time power setpoints over `activation/{assetId}`
  - **Measurements:** 1 Hz telemetry streaming over `measurements/{assetId}` — power, SoC, frequency, aFRR baseline
  - **Task events:** Lifecycle reporting (`STARTED`, `COMPLETED`, `FAILED`, `INVALID`, `UNAUTHORISED`)
  - **Events:** Operational event reporting with severity levels and domain classification

  ### REST API — Delegated Operators (v2)

  - **Authentication:** OAuth2 `client_credentials` grant at `POST /v2/auth/token`
  - **Assets:** `GET /v2/assets` with active specification snapshots per asset
  - **Sites and meters:** `GET /v2/sites` and `GET /v2/sites/{site_id}/meters`
  - **Availability:** `GET /v2/availability` — upward/downward capacity and product availability per time slot
  - **Dispatch tasks:** `GET /v2/dispatch/tasks` — planned schedule with `commitmentId` change detection
</Update>
