## Overview

The HGT platform exposes two protocol layers, each with its own versioning model:

| Layer | Protocol | Version carrier |
|-------|----------|----------------|
| REST API | HTTPS | URL path prefix (`/v2/...`) |
| Real-time API | MQTTS (AsyncAPI) | Topic path segment (`/v2/...`), on the resource API only |

Within a given version, the schemas themselves carry a fine-grained `schema_version` integer for asset specification objects. These three mechanisms work independently and can advance at different rates.

---

## REST API versioning

REST endpoints are versioned via a path prefix. The current version is **v2**.

```
https://api.gridhub.dev/v2/auth/token
https://api.gridhub.dev/v2/assets
https://api.gridhub.dev/v2/sites
https://api.gridhub.dev/v2/dispatch/tasks
```

A future version would introduce new endpoints under `/v3/`, leaving `/v2/` routes intact and operational throughout the deprecation window.

### Rules

- **Non-breaking** changes (new optional fields, new query parameters, new endpoints) are added to the current version without a version bump.
- **Breaking** changes (removed fields, changed response shapes, renamed endpoints) are only made under a new major version.
- Both versions run in parallel during the deprecation period. The `Deprecation` and `Sunset` response headers signal when a version will be withdrawn.

## MQTT topic versioning

MQTT topic paths on the distributed energy resources API embed a version segment. Two versions are live.

The deprecated v1 EV charger and heat pump APIs:

```
{priceZone}/{customerName}/v1/register
{priceZone}/{customerName}/v1/activation/{resourceId}
{priceZone}/{customerName}/v1/power/{resourceId}
```

The current v2 resource API, which replaces both:

```
{priceZone}/{customerName}/v2/register
{priceZone}/{customerName}/v2/activation/{resourceId}
{priceZone}/{customerName}/v2/measurements/{resourceId}
```

Migration is per resource: a resource is on v1 or on v2 depending on which topic prefix it publishes to, and the platform dispatches it on the version it is registered against. No sunset date is set for v1. See [Migrating to v2](/distributed-resources/migration).

The Delegated Operators MQTT API carries no version segment. Its topics are addressed directly, as in `{priceZone}/{customerName}/activation/{assetId}`.

### Message-level versioning

Within a single topic version, individual message schemas may evolve. The v1 EV charger activation channel demonstrates this: its `Activations` topic carries both a **v1** and a **v2** activation message format, differentiated by the presence of `resource_id` in the payload.

```
v1 activation: { event_id, activation, timestamp, power_limit_kw, ends_at }
v2 activation: { event_id, resource_id, activation, timestamp, power_limit_kw, ends_at }
```

When the platform emits an activation, it indicates the message version in the AsyncAPI `messageId` binding. Clients should inspect the payload for the presence of `resource_id` to detect message version at runtime and handle both forms defensively.

## Asset specification versioning

The `specifications` field on assets returned by `GET /v2/assets` is an opaque JSON document. Its shape is governed by the asset `kind` and a `schema_version` integer.

```json title="Asset with schema_version"
{
  "kind": "bess",
  "schema_version": 2,
  "specification": {
    "power": { "type": "static", "unit": "kW", "rated": 2000, "usable": 2000 }
  }
}
```

**Always gate your parsing on `schema_version` and tolerate unknown keys.** The specification schema for a given `(kind, schema_version)` pair is frozen. New fields may be added to future schema versions without changing the `kind`.

## Expanding to a new version

The v2 resource API is the worked example. When a new version is introduced, these artifacts are updated:

<Steps>
  ### New AsyncAPI spec

  A new file is added under `api-reference/asyncapi/`. The v2 resource API added `distributed-resources.yaml`; the v1 specs it replaces are retained and continue to be published.

  ### Updated docs.json navigation

  The new version leads its tab, and the versions it replaces are retitled and moved below it:

  ```json title="docs.json"
  {
    "group": "Distributed Energy Resources (v2)",
    "asyncapi": {
      "source": "/api-reference/asyncapi/distributed-resources.yaml",
      "directory": "api-reference/distributed-resources"
    }
  },
  {
    "group": "EV Chargers (v1, deprecated)",
    "asyncapi": {
      "source": "/api-reference/asyncapi/ev-chargers.yaml",
      "directory": "api-reference/ev-chargers"
    }
  }
  ```

  ### Migration guide

  A page mapping every changed field, and leading with the changes that leave a plausible value on the wire while being wrong. See [Migrating to v2](/distributed-resources/migration).

  ### Changelog entry

  An entry documenting what changed and the migration path. A sunset date is published only when one is set.

  ### Deprecation window

  The old version remains fully operational. The platform publishes on both versions for as long as resources are registered against both.
</Steps>

<Note>
  The AsyncAPI `info.version` (e.g., `3.0.2`) tracks the spec document version, not the topic path version. These are independent. A spec can be updated to `3.0.3` while the topic path remains `/v1/`.
</Note>
